## Current local retest: one-tick pre-load expiry change (23 October 2026)

The latest user log shows several successful restores, including an OTHER item after its ownership handoff. Later that same accepted OTHER item was explicitly removed from an inactive view with `ticksUntilExpiry=70`, opening a pending witness. A same-place OTHER spawn before the next load had matching quantity, `visibleDelta=+51`, and `despawnDelta=+1`. The previous code rejected it immediately because its temporary expiry exceeded the saved deadline; the next `LOADING` reported `saved=0`. The trace compares the same item ID, so it gives no evidence that the ID changed. It also does not establish a special near-despawn state. [RuneLite's TileItem API](https://github.com/runelite/runelite/blob/master/runelite-api/src/main/java/net/runelite/api/TileItem.java) exposes visibility and despawn times but gives no documented identity meaning to this +1 shift.

The local fix permits that +1 only as a provisional **pre-load** observation for a previously accepted, exactly bound OTHER item removed from an inactive view. It needs one unique same-context pile and a load by the next tick. The post-load OTHER replay must be in the active scene and matching instance chunk, with equal visible/despawn shifts of at most one tick from that observation and a final despawn deadline no later than the original saved one. No mark or deadline extension is granted from the provisional spawn alone. A late load, wrong final timer, duplicate pile, inventory gain, or other existing invalidation discards it. This is best-effort continuity: another player's identical same-place item with the same timer pattern remains indistinguishable through the public API, so live testing is still required.

## Performance and lifecycle

Only item/menu/game-state/world-view events and GameTick are subscribed. No ClientTick, scene-wide scans, polling, price lookups, network requests, asset decoding, panel rebuilds, or cross-plugin configuration edits. Idle GameTick checks inventory and the empty tracker; active work is bounded by 28 pending IDs, 28 ground candidates per ID, 256 own tracked objects and 256 GIM candidates (at most 512 cached labels). Inventory counts run only for pending IDs. Group definitions are read once per retained candidate; quantity changes reuse cached classification. Rendering visits own marks and, only when enabled/visible, GIM candidates; filter names/categories/text are cached, category mask/colors are read once per render, tile fill draws once per tile, and disabled/transparent outlines skip model work. A reused small per-tile row map positions labels. The original version cleared all marks on game-state loading; explicit despawn/unload/shutdown cleanup was included.

One/multiple-client CPU, allocation behavior, frame pacing, and native outlines remain live-test requirements. No measured live performance claim is made.

## Remaining live checks and known limits

Run all seven smoke-test groups in `docs/development.md` before claiming live readiness. In particular, own dropped-item ownership and menu semantics, actual item outline alpha, event order, multiple same-ID clicks spanning server ticks, and scene/world-view behavior need game-client verification. GIM mode requires real two-account checks of ownership/visibility transitions, loot inclusion, mixed piles, cap behavior and toggle interaction. It does not backfill pre-existing scene items or discover a transition to GROUP without a new item event; changes away from GROUP suppress existing group marks at render. Consuming a combined own intent on its first confirmed inventory loss can intentionally miss later queued drops. Simultaneous same-item loot/failed Drop/unrelated loss is not perfectly disambiguated. Merged stacks receive a whole-stack mark; the original version cleared own marks on every world/scene loading line. Filters are explicit approximations; native Ground Items text can duplicate this plugin's optional labels. Tile fill colors ground tiles, not model faces.
